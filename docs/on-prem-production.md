# دليل التشغيل الرسمي على سيرفر ويندوز محلي

تشغيل **Projects System Management** داخل شبكة الشركة: البيانات على جهازكم، بدون سحابة، مع مواقع بعيدة تُربَط لاحقاً عبر VPN، وحد أقصى نحو **200 مستخدم**.

هذا الدليل يفترض أن آلة الإنتاج **حاسوب ويندوز له مهام أخرى** (مكتب، ملفات، برامج يومية) وليس Ubuntu Server. لا حاجة لاستبدال نظام التشغيل؛ المطلوب ضبط ويندوز وDocker حتى لا تُطفئ المهام الأخرى الخدمة، ولا تبتلع الخدمة بقية الجهاز.

دليل النشر السحابي التجريبي منفصل: [`staging-deployment.md`](./staging-deployment.md). لا تخلطوا المسارين: هناك البيانات على Supabase السحابي، وهنا البيانات محلية فقط.

---

## 1. اقرأ هذا أولاً

التطبيق طبقتان مستقلتان، وليست برنامجاً واحداً:

```
حاسوب المستخدم (المتصفح)
        │
        │  ملفات ثابتة: HTML / JS / CSS
        ▼
  سيرفر الواجهة على ويندوز     ←  مجلد dist بعد البناء
        │
        │  المتصفح يتصل مباشرةً (ليس عبر سيرفر الواجهة)
        ▼
  سيرفر البيانات (Docker)      ←  Auth + Postgres + Storage
                                  + Realtime + دالة manage-account
```

| حقيقة                                                                        | لماذا تهمّكم                                                                                                  |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| عنوان قاعدة البيانات يُخبز داخل الواجهة **وقت البناء** (`VITE_SUPABASE_URL`) | إن بقي `http://127.0.0.1:54321` فالحاسوب البعيد يفتح الشاشة ثم يفشل، لأن `127.0.0.1` يعني جهازه هو            |
| `npm run dev` و `npm run preview` ليسا تشغيلاً رسمياً                        | وضع تطوير / معاينة للمطوّر فقط                                                                                |
| المواقع غير المربوطة لا تدخل الإنتاج                                         | بلا VPN لا يصل المستخدم البعيد إلا بفتح النظام على الإنترنت — وهذا مرفوض هنا                                  |
| `npx supabase start` كما هو للتطوير ليس إنتاجاً                              | أسرار JWT المحلية معروفة علناً، وStudio إدارة كاملة                                                           |
| ويندوز مكتبي ≠ سيرفر مخصّص                                                   | الإسبات وتحديثات ويندوز وDocker Desktop وإغلاق الجلسة أسباب توقّف شائعة — تُعالَج في القسم 4 دون تغيير النظام |

**سياسة التشغيل**

- البيانات لا تُرفع إلى سحابة Supabase ولا إلى استضافة الواجهة السحابية.
- لا Port Forwarding على الراوتر، ولو «مؤقتاً».
- لا لوحة Studio ولا منفذ Postgres على شبكة المستخدمين.
- المواقع غير المربوطة تنتظر اكتمال VPN ثم تُنشأ حساباتها.
- اسم وصول ثابت (DNS داخلي) منذ اليوم؛ لا تعتمدوا على `192.168.x.x` في البناء.
- هذا الحاسوب مؤقت من ناحية العتاد؛ إن وصل سيرفر لاحقاً تُنقل Docker volumes مع الإبقاء على نفس الاسم إن أمكن.

## 3. ماذا يعني «ويندوز له مهام أخرى» عملياً

الخدمة تعمل **بجانب** الاستخدام اليومي للجهاز، لا بدلاً منه. لذلك:

| الخطر                                       | ما يحدث                                               | المعالجة في هذا الدليل                                                               |
| ------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------ |
| إسبات / إغلاق الغطاء / توفير طاقة           | Docker يتوقف؛ المستخدمون يرون التطبيق ميتاً           | خطة طاقة بلا إسبات أثناء ساعات العمل (القسم 4)                                       |
| تحديث ويندوز يعيد التشغيل                   | انقطاع مفاجئ                                          | ساعات نشاط + إشعار قبل إعادة التشغيل                                                 |
| Docker Desktop لا يعمل إلا بعد تسجيل الدخول | إن لم يدخل أحد الجهاز صباحاً فالخدمة لا تبدأ          | تشغيل Docker عند تسجيل الدخول + سياسة: الجهاز يبقى شغالاً ومسجّل الدخول لحساب الخدمة |
| Docker يبتلع RAM/CPU                        | البرامج الأخرى تتجمّد، أو العكس: ويندوز يقتل الحاويات | سقف ذاكرة/معالج لـ Docker Desktop (القسم 4.3)                                        |
| تطوير على نفس القاعدة الرسمية               | `supabase db reset` يمسح بيانات الشركة                | مستودع التطوير وقاعدة الإنتاج منفصلان دائماً                                         |
| برامج أخرى على المنافذ 80 / 443 / 54321     | البروكسي أو API يفشل في الربط                         | حرّروا هذه المنافذ أو غيّروا منفذ البروكسي مع الإبقاء على الاسم                      |

**الحد الأدنى المقترح للعتاد على جهاز مشترك**

| المورد         | حد أدنى                                           | أفضل إن وُجد                           |
| -------------- | ------------------------------------------------- | -------------------------------------- |
| RAM الجهاز كله | 16 GB (ويندوز + مهام + Docker)                    | 32 GB                                  |
| سقف Docker     | 6–8 GB من الـ RAM، لا «كل الذاكرة»                | 8–12 GB إن كان الجهاز 32 GB            |
| القرص          | SSD مع مساحة للمرفقات (حد الملف في المشروع 50MiB) | قرص بيانات منفصل للنسخ وDocker volumes |
| التشغيل        | الجهاز يبقى مفتوحاً في ساعات العمل على الأقل      | 24/7 مع UPS إن أمكن                    |

عنق الزجاجة لن يكون كود React، بل انقطاع ويندوز وامتلاء القرص وغياب النسخ الاحتياطي.

## 4. تجهيز ويندوز قبل أي نشر

### 4.1 الطاقة وتسجيل الدخول

1. إعدادات الطاقة: **لن ينام** الحاسوب عند توصيل الكهرباء. إن كان محمولاً: إغلاق الغطاء = عدم الإسبات أثناء التوصيل، أو اتركوه مفتوحاً على المكتب.
2. لا تعتمدوا على «تحديث سريع / Fast Startup» إن لاحظتم أن Docker لا يعود بعد إعادة التشغيل — عطّلوه من خيارات الطاقة إن لزم.
3. حساب ويندوز الذي يشغّل Docker: سجّلوا الدخول تلقائياً إلى هذا الحساب فقط إذا كان الجهاز في غرفة مغلقة؛ وإلا أبقوا الجلسة مفتوحة يدوياً في بداية الدوام.
4. Docker Desktop: فعّلوا **Start Docker Desktop when you sign in**. الخدمة في هذا النموذج تبدأ بعد دخول المستخدم، وهذا مقبول طالما الجهاز مكتب يومي وليس راكًا في خزانة بلا جلسة.

### 4.2 تحديثات ويندوز

1. عيّنوا **ساعات النشاط** لتغطي الدوام (مثلاً 07:00–19:00).
2. لا تدعوا التحديث يعيد التشغيل دون علم في منتصف العمل.
3. بعد أي إعادة تشغيل إدارية: تحققوا أن Docker أخضر، ثم أن الواجهة تفتح من جهاز آخر (القسم 13).

### 4.3 Docker Desktop (محرّك البيانات)

1. ثبّتوا Docker Desktop مع خلفية **WSL2** (الوضع المدعوم والمستقر على ويندوز 10/11).
2. Resources: حدّوا الذاكرة والمعالج حتى تبقى مهام المكتب قابلة للاستخدام. لا تتركوا Docker على الحد الأقصى الافتراضي على جهاز 16 GB.
3. Disk image: ضعوا قرص Docker على SSD فيه مساحة؛ امتلاء هذا الملف يوقف Postgres فجأة.
4. فعّلوا إعادة تشغيل الحاويات (`restart: unless-stopped` في Compose) حتى تعود الخدمة بعد إعادة تشغيل Docker نفسه.

**لا تستخدموا مكدس التطوير كما هو.** إما Compose إنتاجي ذاتي الاستضافة، أو مكدس CLI مع أسرار JWT جديدة وربط المنافذ على عنوان الشبكة — وليس مفاتيح الـ demo في `.env.development`.

### 4.4 جدار ويندوز

اسمحوا الوارد فقط لما يحتاجه المستخدم:

| المنفذ                             | الغرض                           | على شبكة المستخدمين    |
| ---------------------------------- | ------------------------------- | ---------------------- |
| 443 (و80 لإعادة التوجيه إلى HTTPS) | الواجهة + API عبر reverse proxy | نعم                    |
| 54321 إن لم يمرّ عبر البروكسي      | API خام (غير مفضّل)             | تجنّبوه؛ مرّروه من 443 |
| 54322 Postgres                     | قاعدة مباشرة                    | **لا**                 |
| 54323 Studio                       | لوحة إدارة                      | **لا** للمستخدمين      |
| 5173 / 4173 تطوير Vite             | —                               | **لا**                 |

أنشئوا قاعدة وارد صريحة لبرنامج البروكسي (Caddy أو Nginx) على 443، لا «السماح لكل شيء».

### 4.5 اسم ثابت وليس IP

احجزوا IP لهذا الحاسوب على الراوتر (DHCP reservation) **و** سجّلوا اسماً داخلياً، مثلاً:

- `https://pms.factory.local` للواجهة
- `https://api.pms.factory.local` للـ API  
  أو مسار واحد خلف نفس الشهادة: الواجهة على `/` والـ API على بادئة واضحة.

البناء يُخاطب هذا الاسم. عند ترقيتكم لسيرفر لاحقاً تُحرّكون الاسم في DNS دون إعادة تعليم المستخدمين لرقم جديد.

## 5. المسار بثلاثة أطوار

جهاز المطوّر (حتى لو كان نفس الحاسوب في وقت آخر) يستخدم `npm run start:local` ضد **قاعدة تطوير**. بيئة الإنتاج: أسرار مختلفة، بلا `seed.sql`، بلا حسابات العرض.

```
الطور 1                    الطور 2                 الطور 3
المصانع المربوطة على       ربط كل موقع بعيد        نقل Docker volumes
حاسوب ويندوز الحالي        بـ VPN ثم الحسابات      إلى سيرفر لاحق
```

### الطور 1 — المواقع المربوطة على شبكة هذا الحاسوب

1. تطبيق القسم 4 بالكامل.
2. تشغيل طبقة البيانات في Docker خلف reverse proxy (القسم 7).
3. بناء الواجهة على العناوين النهائية ونشر `dist` (القسم 8).
4. نسخة احتياطية أولى + تجربة استعادة (القسم 10).
5. حساب مدير شركة حقيقي، ثم تشغيل رسمي للمواقع المربوطة فقط.

### الطور 2 — المواقع البعيدة

لكل موقع، بهذا الترتيب فقط:

1. تشغيل نفق VPN (القسم 6).
2. من حاسوب هناك: فتح عنوان الواجهة، تسجيل دخول، رفع مرفق، ثم التأكد أن الإشعار يظهر **بدون** تحديث الصفحة (اختبار Realtime عبر النفق).
3. بعد النجاح: إنشاء حسابات ذلك الموقع من شاشة الحسابات داخل التطبيق.

### الطور 3 — سيرفر لاحق دون إعادة المشروع

لا يهم إن كان السيرفر لاحقاً ويندوز أو Linux. اليوم تثبّتون:

- بيانات في Docker volumes بأسماء ثابتة
- إعدادات Compose/env خارج Git
- نسخة احتياطية = قاعدة + Storage + `dist` + ملفات الإعداد

النقل: توقف قصير → نسخ الـ volumes → تشغيل نفس الـ Compose → الإبقاء على `pms.factory.local` → إعادة بناء الواجهة **فقط إذا تغيّر العنوان**.

## 6. ربط المواقع البعيدة

البيانات تبقى على حاسوب ويندوز في الشركة. النفق ينقل حركة مشفّرة فقط.

| الخيار                      | متى يناسب                                         | ملاحظة                                                        |
| --------------------------- | ------------------------------------------------- | ------------------------------------------------------------- |
| **Tailscale**               | مدير شركة؛ أجهزة متفرقة؛ ويندوز على الطرفين       | الأسهل؛ ثبّتوا العميل على السيرفر وعلى حواسيب المواقع البعيدة |
| **WireGuard موقع-إلى-موقع** | الراوتر يدعمه؛ الموقع كله يجب أن يُرى كشبكة واحدة | قد لا يحتاج المستخدم تثبيتاً                                  |
| **Headscale**               | مثل Tailscale وخادم التنسيق عندكم                 | جهد أكبر                                                      |
| فتح المنافذ للإنترنت        | لا                                                | مرفوض في هذا الدليل                                           |

على ويندوز: Tailscale يعمل كخدمة ويمكنه البقاء بعد تسجيل الدخول إن ضُبط كذلك. اختبروا أن `https://pms.factory.local` (أو اسم Tailscale MagicDNS) يفتح من الموقع البعيد **قبل** إنشاء المستخدمين هناك.

## 7. طبقة البيانات و reverse proxy

المتصفح على جهاز المستخدم هو من يتصل بـ Supabase، وليس «سيرفر الواجهة» فقط. لذلك يجب أن يفتح المتصفح البعيد عنوان الـ API فعلياً.

**مخطط موصى به على ويندوز**

```
المستخدم ──443──► Caddy (حاوية Docker أو برنامج ويندوز)
                    ├── /            → ملفات dist (SPA)
                    └── /auth /rest /storage /functions /realtime
                                    → API داخل Docker
```

| العنصر                          | المطلوب في الإنتاج                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| أسرار JWT                       | مولَّدة لهذه البيئة؛ ليست مفاتيح `.env.development`                                  |
| مفتاح الواجهة                   | anon / publishable فقط                                                               |
| `service_role`                  | داخل الخادم / Edge Function فقط — لا Git ولا الواجهة                                 |
| Studio `:54323`                 | مربوط بـ localhost على جهاز السيرفر، أو عبر VPN للمدير فقط                           |
| Postgres `:54322`               | داخل Docker فقط                                                                      |
| `enable_signup`                 | مغلق؛ الحسابات عبر دالة `manage-account`                                             |
| Auth `site_url` و Redirect URLs | عنوان الواجهة النهائي `https://pms.factory.local`                                    |
| Realtime                        | البروكسي يمرّر WebSocket (`Upgrade`)                                                 |
| الدالة `manage-account`         | شغّالة في نفس البيئة وإلا إنشاء الحسابات يفشل                                        |
| البريد                          | SMTP حقيقي أو الاعتماد على توليد كلمة المرور من شاشة الحسابات (Inbucket للتطوير فقط) |
| `seed.sql`                      | ممنوع على بيانات الشركة                                                              |

Caddy على ويندوز: إما حاوية في نفس Compose (أسهل للنقل لاحقاً) أو [Caddy لويندوز](https://caddyserver.com/) كخدمة. Nginx أو IIS يعملان إن كانا موجودين مسبقاً؛ المطلوب واحد: HTTPS، و`try_files` / fallback إلى `index.html` لمسارات React Router، وWebSocket للـ Realtime.

**لا تتركوا `npm run preview --host` للمستخدمين.** ذلك سيرفر معاينة، ليس استضافة رسمية.

## 8. بناء الواجهة على ويندوز

من جذر المستودع، انسخوا القالب ثم املأوا قيماً **إنتاجية**:

```powershell
copy .env.production .env.production.local
```

```env
VITE_APP_ENV=production
VITE_SUPABASE_URL=https://api.pms.factory.local
VITE_SUPABASE_PUBLISHABLE_KEY=<مفتاح anon لهذه البيئة فقط>
```

`VITE_SUPABASE_URL` يجب أن يفتحه متصفح حاسوب **آخر** على الشبكة أو VPN، لا متصفح السيرفر وحده.

```powershell
npm run verify
npm run build
```

المخرجات في `dist/`. انسخوها إلى مجلد نشر ثابت (مثلاً `C:\pms\www`) لا إلى مجلد التطوير الذي قد يُمسَح.

متغيرات `VITE_*` تُدمج وقت البناء. تغيير الاسم أو البروتوكول لاحقاً = إعادة `npm run build` واستبدال محتويات مجلد النشر. صفحة HTTPS لا تنادى API على HTTP (mixed content) — اجعلوا الاثنين HTTPS.

هذا المشروع يستخدم Realtime للإشعارات والتعليقات وتحديثات المشروع، وStorage للشعار ومرفقات المقترحات. عنوان API الخطأ يكسر الملفات والتحديث اللحظي حتى لو «الصفحة تفتح».

## 9. قائمة تحقق التنفيذ

لا تقفزوا إلى حسابات المواقع البعيدة قبل البند 12.

- [ ] 1. فصل قاعدة التطوير عن قاعدة الإنتاج (حتى على نفس الحاسوب: مشروع Docker / بيانات مختلفة).
- [ ] 2. تطبيق إعدادات ويندوز: طاقة، تحديثات، سقف Docker، جدار ناري، حجز IP + DNS (القسم 4).
- [ ] 3. توليد أسرار JWT ومفاتيح anon/service جديدة.
- [ ] 4. تشغيل طبقة البيانات في Docker مع `restart: unless-stopped` خلف Caddy على 443.
- [ ] 5. تطبيق الهجرات على قاعدة إنتاج فارغة نظيفة (لا تعدّلوا ملفات هجرة قديمة).
- [ ] 6. تشغيل `manage-account` والتأكد من buckets التخزين.
- [ ] 7. ضبط Auth Site URL و Redirect URLs على عنوان الواجهة النهائي.
- [ ] 8. ملء `.env.production.local` واختبار الرابط من جهاز ثانٍ.
- [ ] 9. `npm run verify` ثم `npm run build` ثم نشر `dist` مع SPA fallback وWebSocket.
- [ ] 10. إغلاق 54322 و 54323 عن الشبكة في جدار ويندوز.
- [ ] 11. نسخة احتياطية أولى + تجربة استعادة (القسم 10).
- [ ] 12. حساب مدير الشركة الحقيقي (ليس حساب الـ demo).
- [ ] 13. تشغيل رسمي للمواقع المربوطة أسبوعاً.
- [ ] 14. لكل موقع بعيد: VPN → اختبار الدخول والمرفقات والإشعارات → ثم المستخدمون.
- [ ] 15. لاحقاً: نقل الـ volumes مع الإبقاء على نفس الاسم إن أمكن.

## 10. النسخ الاحتياطي (مدير الشركة)

يومياً، تلقائياً إن أمكن، إلى قرص خارجي أو NAS **ليس** قرص ويندوز نفسه:

1. قاعدة Postgres (dump أو نسخ حجم Docker الخاص بقاعدة البيانات).
2. ملفات Storage (الشعار + مرفقات المشاريع).
3. ملفات Compose و `.env` الإنتاجية (ليست في Git العام).
4. نسخة مجلد `dist` المنشور حالياً.

على ويندوز: مهمة في **Task Scheduler** بعد منتصف الليل، بشرط أن الجهاز لا ينام في ذلك الوقت وإلا لن تعمل المهمة. إن كان الحاسوب يُطفأ مساءً، اجعلوا النسخ عند نهاية الدوام قبل الإطفاء، لا في الساعة 03:00.

**قاعدة:** النسخ الذي لم تُجرَّب استعادته مرة على مجلد فارغ قبل يوم الإطلاق ليس نسخة احتياطية.

فحص أسبوعي قصير (~15 دقيقة):

1. هل `https://pms.factory.local` يفتح من جهاز مستخدم؟
2. هل تسجيل الدخول يعمل؟
3. هل أيقونة Docker Desktop خضراء بعد أي إعادة تشغيل؟
4. هل تاريخ آخر نسخة هو اليوم أو أمس؟
5. هل مساحة القرص (ويندوز + قرص Docker) تحت ~70٪؟
6. هل الإشعارات تتحدث دون تحديث الصفحة؟

عند الشك في حساب مدير: إعادة تعيين كلمة المرور من شاشة الحسابات (الدالة في هذا المشروع تلغي الجلسات القديمة).

## 11. مخاطر الانهيار على ويندوز المشترَك

| الخطر                              | لماذا يحدث هنا                       | الإغلاق                                                                         |
| ---------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| إسبات أو إغلاق الغطاء              | حاسوب مكتبي/محمول بمهام أخرى         | منع الإسبات على الكهرباء؛ سياسة «يبقى شغالاً أثناء الدوام»                      |
| إعادة تشغيل التحديث                | ويندوز يعيد التشغيل وحده             | ساعات النشاط؛ تحقق بعد كل إعادة تشغيل                                           |
| Docker لا يعمل حتى الدخول          | Docker Desktop مرتبط بالجلسة         | تشغيل عند Sign in؛ لا تعتمدوا على جهاز بلا مستخدم مسجّل                         |
| نفاد RAM                           | ويندوز + مكتب + Docker + 200 جلسة    | سقف Docker؛ 16 GB حد أدنى، 32 GB أفضل                                           |
| امتلاء قرص المرفقات أو صورة Docker | حد 50MiB لكل ملف يتراكم              | مراقبة القرص؛ تنظيف/أرشفة؛ لا تضعوا Docker على قرص شبه ممتلئ                    |
| أسرار التطوير في الإنتاج           | مفاتيح local معروفة                  | أسرار جديدة؛ لا seed على بيانات حقيقية                                          |
| موقع بعيد قبل VPN                  | ضغط لفتح منفذ الراوتر                | الموقع ينتظر؛ لا Port Forwarding                                                |
| `db reset` على الإنتاج             | أوامر التطوير على نفس الحاسوب        | مجلد بيانات إنتاج خارج مستودع التطوير؛ لا تشغّلوا `npm run supabase:reset` هناك |
| تغيير IP                           | البناء يخاطب العنوان القديم          | DNS ثابت؛ حجز DHCP                                                              |
| Postgres مكشوف                     | تجاوز RLS                            | جدار ويندوز يغلق 54322                                                          |
| شهادة TLS أو HTTP مختلط            | المتصفح يرفض                         | HTTPS للواجهة والـ API معاً                                                     |
| VPN ضعيف                           | Realtime ينقطع فيبدو التطبيق معلّقاً | اختبروا الإشعارات من الموقع البعيد قبل الإطلاق هناك                             |
| حساب مدير مشترك                    | تسريب واحد = كل البيانات             | حساب شخصي لكل مدير؛ كلمات مرور أقوى من حد التطوير (6 أحرف)                      |

تحديث الإنتاج: نسخة احتياطية قبل كل هجرة، ثم تطبيق الهجرات الجديدة فقط. احتفظوا بـ `dist` السابق للرجوع عن الواجهة دون لمس القاعدة.

## 12. ما الذي لا تفعلوه

- لا تشغّلوا المستخدمين على `npm run dev` أو `vite preview`.
- لا تضعوا `VITE_SUPABASE_URL=http://127.0.0.1:54321` في بناء يصل إليه غير جهاز المطوّر.
- لا تضعوا `service_role` في الواجهة أو في Git.
- لا تنشروا Studio على الشبكة.
- لا تفتحوا منفذ الراوتر للإنترنت العام.
- لا تشغّلوا `supabase db reset` / `npm run supabase:reset` على بيانات الشركة.
- لا تبنوا الواجهة على IP قد يتغيّر بعد توصيل كابل أو راوتر جديد.

## 13. تحقق من جهاز آخر (إلزامي قبل الإطلاق)

من حاسوب على نفس الشبكة (ليس السيرفر):

1. الصفحة الرئيسية لا تعرض «Supabase: not configured».
2. تسجيل دخول بحساب مدير حقيقي.
3. إنشاء حساب تجريبي عبر شاشة الحسابات (يفحص `manage-account`).
4. رفع مرفق على مقترح (يفحص Storage).
5. إجراء يولّد إشعاراً والتأكد أنه يظهر دون تحديث الصفحة (يفحص Realtime وجدار ويندوز والبروكسي).
6. تحديث الصفحة على مسار مثل `/projects/...` لا يعطي 404 (يفحص SPA fallback).
7. مستخدم محدود الدور لا يرى خارج نطاقه (يفحص أنكم على قاعدة الإنتاج ذات RLS وليس وضعاً مفتوحاً).

## 14. أوامر الواجهة في هذا المستودع

| الأمر                    | الاستخدام                                                  |
| ------------------------ | ---------------------------------------------------------- |
| `npm run start:local`    | تطوير فقط، ضد قاعدة التطوير                                |
| `npm run verify`         | فحص قبل أي بناء إنتاج                                      |
| `npm run build`          | بناء إنتاج من `.env.production` + `.env.production.local`  |
| `npm run preview`        | معاينة محلية للمطوّر، ليست استضافة المستخدمين              |
| `npm run supabase:reset` | يمسح القاعدة المحلية ويُعيد الـ seed — **ليس** على الإنتاج |
