# قصص المستخدمين الحالية — نظام إدارة ومتابعة المشاريع

تاريخ التوليد: **2026-09-07**  
الغرض: ملف مراجعة للمنتج يعكس ما هو **منفّذ فعلياً** في التطبيق، وليس فقط مسودة الـ PRD.

المصادر:

- وثيقة Notion: [Projects Management system](https://app.notion.com/p/3a50d8e17e2280139e66d2e86dbd456a) (US-01 إلى US-06)
- التطبيق الحالي: المسارات، الصلاحيات، والحوكمة في `src/` + RLS

الحالة: كل القصص أدناه **منفّذة** ما لم يُذكر خلاف ذلك في قسم «غير منفّذ / مؤجّل».

---

## 1. الأدوار والنطاق

| الدور                                | النطاق                     | الشاشات الرئيسية                                                                         |
| ------------------------------------ | -------------------------- | ---------------------------------------------------------------------------------------- |
| **مدير الشركة** (`company_director`) | كل المصانع وكل المشاريع    | لوحة القيادة، المشاريع، التنبيهات الحرجة، الحسابات، المصانع، الإعدادات                   |
| **مدير المصنع** (`factory_manager`)  | مصنعه فقط                  | لوحة القيادة، المشاريع، التنبيهات الحرجة، حسابات مدراء المشاريع في مصنعه، إعدادات الحساب |
| **مدير المشروع** (`project_manager`) | المشاريع المُسندة إليه فقط | لوحة القيادة، المشاريع المُسندة، التنبيهات الحرجة، إعدادات الحساب                        |

التسلسل: شركة ← مصنع ← مشروع ← مراحل ← مهام ← تعليقات / نشاط / مرفقات / مالية.

---

## 2. دورة حياة المشروع

```
draft → proposed → approved → in_progress → completed
                 ↘ rejected → draft (إعادة تقديم)
                 approved / in_progress ⇄ paused
```

قواعد الحوكمة الحالية:

- بعد الاعتماد تُجمَّد الميزانية والتواريخ والكود؛ أي تعديل يتم عبر **طلب تغيير**.
- التمويل والعمليات المالية تظهر بعد الاعتماد فقط (تبويب المالية).
- مدير المصنع يصمّم المراحل في `approved`/`in_progress`/`paused`؛ مدير المشروع المسند يعدّ المهام من `approved` (تخطيط `todo`) وينفّذها بعد البدء.
- بدء التنفيذ وإيقافه واستئنافه وطلب الإغلاق: مدير المصنع (والإغلاق النهائي: مدير الشركة).
- مناقشة المقترح: مدير الشركة ↔ مدير المصنع فقط؛ مدير المشروع يرى ولا يعلّق في هذه المرحلة.

## 3. قصص الـ PRD الأصلية

هذه القصص الست من وثيقة المتطلبات، مع شروط القبول كما هي اليوم في التطبيق.

### US-01 — رؤية تجميعية للمصانع والمشاريع

**كـ** مدير شركة  
**أريد أن** أستعرض المشاريع ونسب إنجازها ومؤشرات الانتباه في لوحة واحدة  
**حتى أستطيع** تقييم الأداء العام والتدخل عند وجود خلل

**شروط القبول (الحالية):**

- لوحة قيادة scoped حسب الدور (المدير يرى الكل).
- بطاقات انتباه: مهام متعثرة، متأخرة، مقترحات بانتظار المراجعة، مواعيد قريبة، مشاكل مراحل، مشاريع ناقصة التمويل، مشتريات متأخرة.
- رسوم بيانية (حالة المشروع / حالة المهام / شرائح الإنجاز / أكثر المشاريع تعثراً) مع نقر للفلترة.
- جدول استكشاف قابل للبحث والفلترة حسب الحالة، المصنع، نطاق الإنجاز، التعثر، التأخير، مشاكل المراحل، التمويل، المشتريات.
- نسبة الإنجاز تُحسب تلقائياً من أوزان المراحل والمهام.

### US-02 — تقديم مقترح مشروع

**كـ** مدير مصنع  
**أريد أن** أنشئ مقترح مشروع (فكرة + ميزانية + مدة + مدير مشروع + مرفقات)  
**حتى أستطيع** رفعه للإدارة العليا للاعتماد

**شروط القبول (الحالية):**

- حفظ مسودة (`draft`) أو إرسال (`proposed`).
- عند الإرسال حقول إلزامية: الكود، العنوان، الوصف، الميزانية، العملة، تاريخ البداية والنهاية، مدير المشروع المعيَّن.
- الكود فريد داخل المصنع (`FACTORY/CODE`).
- إرفاق ملفات داعمة (سحب وإفلات).
- إشعار داخل التطبيق لمدير الشركة عند الإرسال.
- يمكن تعديل المسودة أو المقترح المرفوض وإعادة الإرسال.

### US-03 — اعتماد أو رفض المقترح

**كـ** مدير شركة  
**أريد أن** أوافق على المقترح أو أرفضه مع سبب  
**حتى يبدأ** التخطيط التنفيذي أو يُعاد المقترح للمصنع

**شروط القبول (الحالية):**

- الاعتماد يغيّر الحالة إلى `approved` (حوار ملخص: الميزانية، مدير المشروع، عدد المرفقات).
- الرفض يغيّر الحالة إلى `rejected` مع سبب ظاهر لمدير المصنع.
- مناقشة المقترح بالتعليقات بين المدير ومدير المصنع قبل القرار.
- إشعار لمدير المصنع بالنتيجة.

### US-04 — تقسيم المشروع إلى مراحل بأوزان

**كـ** مدير مصنع  
**أريد أن** أقسّم المشروع المعتمد إلى مراحل بأوزان وميزانيات وتواريخ  
**حتى** ينتظم العمل وتُحسب نسبة الإنجاز بدقة

**شروط القبول (الحالية):**

- مجموع أوزان المراحل = 100%.
- مجموع ميزانيات المراحل = ميزانية المشروع.
- تواريخ المرحلة داخل جدول المشروع.
- كتابة المراحل بعد الاعتماد وقبل/أثناء التنفيذ (`approved` / `in_progress` / `paused`).
- بدء التنفيذ لا يُتاح إلا بعد جاهزية المراحل (أوزان، ميزانيات، تواريخ).
- غياب المهام تحذير في حوار البدء وليس مانعاً.

### US-05 — مهام بحالات وتعثر لحظي

**كـ** مدير مشروع  
**أريد أن** أنشئ مهاماً داخل كل مرحلة وأغيّر حالتها (`todo` / `in_progress` / `blocked` / `done`)  
**حتى** أتابع التنفيذ اليومي وأُظهر الانسداد فوراً

**شروط القبول (الحالية):**

- كانبان بالسحب والإفلات + قائمة حالة للوحة المفاتيح.
- `blocked` يتطلب سبب التعثر ويولّد تنبيهاً حرجاً وإشعاراً.
- `done` يفتح حوار إكمال (تاريخ نهاية فعلي + تكلفة مصروفة + مبرر عند تجاوز الموعد/التكلفة).
- تحديث لحظي عبر Realtime.
- أوزان المهام داخل المرحلة = 100% عند وجود مهام.
- إعداد المهام ممكن بعد الاعتماد وقبل البدء (`approved`)؛ تغيير الحالة على الكانبان بعد `in_progress` / `paused`.

### US-06 — تعليقات على المشروع / المرحلة / المهمة

**كـ** أي مستخدم مخوّل  
**أريد أن** أضيف ملاحظة على الكيان المناسب  
**حتى** يتم التواصل دون اجتماعات أو واتساب

**شروط القبول (الحالية):**

- ظهور اسم الكاتب، دوره، والوقت.
- تحديث لحظي.
- إشارة `@` مع إشعار للمذكور.
- في مرحلة المقترح: المدير ومدير المصنع فقط.
- بعد الاعتماد: من يستطيع فتح المشروع يمكنه التعليق (بما فيه المكتمل).

## 6. غير منفّذ / مؤجّل (للمقارنة مع الـ PRD)

هذه العناصر وردت في الرؤية أو الـ backlog وليست قصص مستخدم حالية في التطبيق:

- تطبيقات موبايل أصلية (Flutter).
- شبكة بطاقات المصانع كخريطة فروع مستقلة (المدير يرى فلتر مصنع داخل لوحة موحّدة).
- استيراد Excel / حقول مشروع مخصصة / جدولة Mina.
- إشعارات بريد أو دفع خارجي.
- أعلام ميزات في `app_settings` لوحدات قيد العمل.
- اختبارات E2E (Playwright) ولقطات RLS كضمان للمنتج وليست قصة مستخدم.

فروقات مهمة عن نص الـ PRD الأصلي:

- **الموافقة على المقترح:** مدير الشركة فقط (كانت تجربة قصيرة تعطيها لمدير المشروع ثم أُعيدت).
- **تعيين PM:** يتم عند تقديم المقترح، لا بعد الاعتماد كخطوة منفصلة إلزامية (يمكن إعادة الإسناد لاحقاً).
- **المدة:** تاريخ بداية/نهاية مقترحان، لا حقل «مدة بالأيام» وحده.
- **المالية:** طبقة كاملة بعد الاعتماد لم تكن في US-01–US-06.

## 7. اقتراح مراجعة

عند المراجعة يُفضَّل التركيز على:

1. هل تقسيم الصلاحيات في القسم 5 يطابق توقّع الإدارة؟
2. هل تجميد العقد + طلب التغيير مقبول بدل تعديل حر بعد الاعتماد؟
3. هل إخفاء التمويل عن شاشة المقترح واضح للمستخدم؟
4. هل مدير المشروع يجب أن يناقش المقترح أم يبقى مشاهداً فقط؟
5. هل طلب الإغلاق من مدير المصنع ثم تأكيد المدير كافٍ، أم يُطلب دور PM؟
